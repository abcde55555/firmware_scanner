# 开源二进制 SCA 如何恢复固件组件身份与版本

日期：2026-11-18。范围：仅核对 EMBA、cve-bin-tool、Syft 的官方文档及代码；未运行这些工具或固件，也未下载参考语料。下文把“识别到一个文件”和“识别到文件中包含的第三方组件”分开讨论。

## 结论先行

当前版本检出覆盖不满足用户的产品可用目标。项目当天的实验报告显示，native 记录中只有 Allwinner 的 21/312、Android system 的 27/774 有版本候选证据（分别约 6.7% 和 3.5%）；这只是输出证据覆盖率，不是真值集上的版本召回率。[项目实验记录](function-version-experiment-results-2026-11-18.md)

下述开源工具使用包管理器/归档元数据、编译器写入的构建元数据，以及每个组件单独维护的身份和版本规则。文件哈希、节哈希、函数级特征需要可比较的参考样本库才有判别力。增加文本规则可以覆盖更多有可见标记的组件；当这些标记已被剥除或从未嵌入时，还需要代码参考等其他信号。这部分属于架构与证据可得性缺口，不只是规则数量问题。

这里说的“行业做法”是对所引用源码/文档中机制的归纳。本文没有对这些工具做固件实测，也不把项目或工具的宣传性覆盖描述当成效果验证。

## 各工具依靠的信号

### EMBA：包信息优先，字符串规则兜底

EMBA 的官方识别说明列出多个独立来源：dpkg/opkg/RPM 数据库、包归档，以及 Python、Node、Rust、Java 等生态元数据；没有这些信息时，它从二进制可打印字符串中匹配逐组件维护的 JSON 规则，并从匹配上下文提取 vendor/product/version。规则可组合多个字符串条件，以减少仅凭弱版本号命中的误报。EMBA 文档也明确指出这种方式需要每个项目维护规则，新版本或新项目会造成规则失配。[EMBA 识别机制与规则维护说明](https://github.com/e-m-b-a/emba/wiki/Increase-component-identification-rate)

这份文档没有为“通用文件哈希/函数指纹即可恢复任意库及精确版本”提供证据。其静态兜底核心是字符串与手写识别规则；用户态/整机模拟属于额外动态渠道，不能等同于离线静态识别。

### cve-bin-tool：每个 checker 定义身份线索和版本表达式

cve-bin-tool 的官方文档说明，自动检测由 binary checker、语言生态文件和归档提取组成，并列出有 checker 的组件及可读的生态清单/锁文件格式。以 OpenSSL checker 为例，身份线索是文件名（`libssl.so.*`、`libcrypto.so`）和内容模式，版本来自带上下文的 OpenSSL 版本正则。也就是说，它依赖 checker 对目标组件的先验规则，不是对任意 ELF 做通用组件相似性检索。[组件检测与支持的输入](https://github.com/ossf/cve-bin-tool/blob/main/doc/README.md)；[OpenSSL checker 源码](https://github.com/ossf/cve-bin-tool/blob/main/cve_bin_tool/checkers/openssl.py)

该项目的文档明示限制：扫描器只检查库签名与版本信息，不分析代码细节；被混淆的信息会导致失效，也无法据版本号识别回移补丁。checker 列表广不代表覆盖率已在目标固件上验证，更不等于漏洞检出效果已经验证。[cve-bin-tool 限制说明](https://github.com/ossf/cve-bin-tool/blob/main/doc/README.md#limitations)

### Syft：文件 catalog 与组件 catalog 是不同任务

Syft 的 executable cataloger 先按可执行文件 MIME 类型枚举文件，再解析 ELF/PE/Mach-O 格式和可用的可执行文件属性。此路径产物是 executable/file 记录；**单凭枚举到 ELF 并不代表已识别其静态链接的 OpenSSL、zlib 等第三方组件**。[Syft executable cataloger 源码](https://github.com/anchore/syft/blob/main/syft/file/cataloger/executable/cataloger.go)

组件识别由专门 cataloger 完成。Syft 的 Go binary cataloger 从 Go 编译器的 build info 读取主模块与依赖模块；版本可来自构建设置、链接参数等。主模块版本缺失时，源码提供可选的内容正则回退，但注释明确承认这可能误报。Syft 维护者在官方 issue 中解释，通用版本字符串回退曾不够可靠，因此默认关闭；遇到未知版本优于把依赖中的其他版本字符串错赋给主程序。[Go build info cataloger 源码](https://github.com/anchore/syft/blob/main/syft/pkg/cataloger/golang/parse_go_binary.go)；[Syft 维护者对 UNKNOWN 与版本字符串回退的说明](https://github.com/anchore/syft/issues/4078)

上述 Syft 源码证明的是它有针对 Go 构建元数据的组件识别路径，以及 executable 文件枚举路径的边界；不能据此推断它对 stripped C/C++ 静态库也有等价的通用身份/版本恢复能力。

## 是规则库问题，还是架构缺口？

两者都有，且需分层处理：

1. **规则覆盖不足**：如果二进制仍包含稳定 banner、路径/文件名、包元数据或明确的版本 getter，而扫描器没有对应 checker、提取规则或格式解析器，扩充规则确实能提高覆盖。EMBA 和 cve-bin-tool 都把逐组件规则作为静态识别的主要渠道。
2. **可观察信号不足**：如果组件被静态链接、符号被剥除、字符串删除或混淆、厂商改写 banner，已有 checker 也可能没有输入可匹配。新加更多正则只能增加误命中机会，不能创造不存在的证据。cve-bin-tool 将混淆列为限制；Syft 对不可靠的通用版本字符串回退选择默认拒判。
3. **缺少参考库属于另一类架构缺口**：要用文件/函数指纹识别 stripped 代码，必须有来源可追溯的多版本参考构建样本、特征提取/相似度算法、架构与编译选项处理、冲突及未知策略。单一 `.text`/`.rodata` 哈希不是跨编译器、配置和厂商补丁的通用版本标识。本文所核对的 EMBA、cve-bin-tool 和 Syft 源码没有显示它们以通用函数指纹参考库作为上述静态识别路径的替代品；这不是声称其全部生态或插件均无相关能力。

因此，把当前低覆盖归结为“规则还不够多”并不准确；只改成“上函数指纹就能解决”同样没有证据。身份识别与精确版本判定应分别评估：已有足够证据识别组件时，版本仍可能未知；出现一个版本字符串时，也不能自动证明字符串属于当前文件的主组件。

## 对本项目的三项具体改变

1. **把结果拆成可审计的证据等级与两阶段结论。** 每条文件观测保留路径、摘要、宿主/容器路径、组件身份证据、版本证据、来源规则和冲突；分别输出“已识别组件”“版本候选”“正式版本”与“未知/冲突”。字符串、文件名、导入符号、定义符号、包数据库和构建元数据不能混成同一可信级别。默认拒绝将无归属上下文的版本串提升为正式 BOM 版本。
2. **将常见组件规则产品化维护，并用正负例门槛扩库。** 优先对覆盖目标固件常见组件的 checker/JSON 规则补充身份线索和版本提取规则；每条规则配命中样本、反例、版本来源与适用格式。身份规则可只输出组件名，缺版本时明确未知。按组件家族维护规则覆盖和误报，而不是用“规则条数”或“文件数”作识别率。
3. **为无标记 stripped 二进制单独建设参考样本路线。** 先选少量高价值库，保存可验证上游版本、源码提交、架构、编译器/选项与产物哈希；验证函数/基本块特征在跨架构、优化和厂商补丁下的稳定性，再以留出版本和厂商固件测精确率、召回率、拒判率。没有这样的参考语料和留出评估前，不把函数指纹原型当产品覆盖。

## 两个边界

1. **版本号不等于补丁状态。** 回移补丁可让旧版本包含修复；厂商分支也可能沿用上游版本号。应保留观测到的版本、厂商/构建信息、补丁证据与漏洞适用性为不同字段，不能单靠版本字符串下结论。
2. **未知是有效结果，文件枚举也不是组件清单。** 对缺少可靠身份/版本证据的文件，输出未知并解释证据缺口；对识别到的 ELF 数量，不得称为已识别第三方组件数量或版本覆盖率。工具源码/文档说明的是实现路径，实际命中率和误报率仍须在有真值的目标固件集上独立测量。

## 核验范围与未核验事项

已核对的源码/文档能够支持本文对各工具数据入口、checker/字符串规则、Syft Go build metadata、文件枚举路径及未知版本处理的描述。未安装或运行工具；未扫描、执行、上传固件；未评估工具的实际组件召回率、版本准确率、误报率或性能；未下载大型参考语料；也未验证所列工具当前发布版本在任一具体固件上的效果。源码能证明“实现了什么路径”，不能单独证明“在实际样本上达到什么效果”。
