# 商用二进制 SCA 的固件组件与版本识别机制

日期：2026-11-18

范围：仅查商用二进制 SCA/固件分析厂商的一手公开资料，选取 Black Duck Binary Analysis、Finite State、Binarly。这里调查的是厂商公开披露内容，不代表对产品进行过独立扫描或验证。没有把厂商宣传中的覆盖率、准确率或“ground truth”用作本项目性能结论。

## 结论

商用品不是靠一个通用指纹直接“读出版本”。公开材料显示，它们组合固件展开/文件识别、组件参考知识库、二进制签名或代码分析、二进制内版本信息、漏洞知识与 SBOM 流程。成熟产品也会遇到无法确认精确版本的情况：Black Duck 明确提供未知版本状态和时间戳匹配；Finite State 的公开更新记录披露过版本平票、漏版本和错误版本修复。版本覆盖是持续构建参考数据和改进证据解释的工程，不是补足几条字符串规则就能一次完成。

对本项目，主要投入应转向带来源的多版本参考语料、代码匹配和版本差异验证，并补齐容器展开范围。现有结果仍不满足用户的产品可用目标。商用产品是可比较的候选方案；其在本项目上的覆盖必须用同两镜像实测，并检查输出证据能否回到固件内具体文件/位置。

## 各厂商资料能确认什么、不能确认什么

### Black Duck Binary Analysis

公开资料中机制披露最具体：结果可展示匹配方法；官方列有文件指纹签名、JAR/文件 checksum、包管理器数据库和嵌入式 PE 元数据等识别方式。精确版本无法确定时，产品可保留未知版本并用时间戳匹配漏洞。它还说明公共知识库不能识别自身不含的组件，且有 Vendor Components 用于组织内学习私有组件。由此可见，“大型参考库 + 多路匹配 + 明确拒判/降级”是一个可核查的产品模式，但公开文档没有给出精确版本的独立准确率，也未公开签名算法和编译归一化。

### Finite State

产品材料公开了固件解包、静态链接/修改组件识别、二进制 SCA 与 SBOM 等能力；产品页所列架构数量属于厂商自报。更具体的版本边界来自官方更新日志：某些构建能够直接导出版本；另一些版本缺失或发生平票，厂商修复了部分固件组件的版本选择。它表明持续按真实固件修正规则和消歧很重要，但日志未给出精确底层技术，不能推断其使用某个私有指纹/模型，更不能把修复记录当成整体准确率。

### Binarly

官方公告明确区分“固件相似度比较”“依赖/SBOM 分析”和“深度漏洞分析”三个目标。相似度用于构建间变更检测，不必然等于组件版本识别；漏洞代码模式也不必然给出上游发布版本。公开材料对高层结果说明较多，版本参考库、代码特征、相似度阈值、跨编译器归一化和拒判策略仍未知。黑盒试用时应要求厂商把这几项变成可回答的问题，而不接受“识别率”单一数字替代。

## 黑盒 POC 验收建议

目标是回答“它在这两份已知镜像上能否可靠报告组件版本”，而非验证整个市场或宣传数字。当前项目已有 Allwinner Android 镜像和 Android `system.img` 的扫描与人工核验材料；其中有高置信版本检查点、应保持未知的检查点、多版本同名组件、APK 内嵌库、覆盖告警及一个复杂 Protobuf 版本边界案例。POC 可用同两份镜像，但必须固定原始文件哈希、扫描入口/分区、产品版本、解包范围、配置与扫描日期。禁止把当前产品的候选输出直接当作真值。

### 盲测设置

1. **第三方建立金标准**：扫描操作人员拿到随机代号镜像；另由不操作厂商产品的核验人员按真实文件证据标注。每个点记录镜像路径、文件 SHA-256、组件身份、精确上游/厂商版本（若有）、版本来源、是否有本地补丁证据、真值置信等级及原因。精确版本由可信版本字符串、已核验版本函数/源码构建证据或独立人工逆向等支撑；仅凭被测产品的输出、漏洞匹配或文件名不可定真值。
2. **冻结扫描范围**：同一镜像输入及同一分区范围；记录解包成功、未识别/加密/超限文件数和字节数、重复扫描结果。厂商产品不可直接接收完整固件时，确保双方分析的是同一组由审计人员抽取的二进制文件，并单列这种范围缩减。
3. **不透露检查点**：厂商获得两份匿名镜像及正常产品操作所需信息，不告知真值名单、容易识别的目标库或预期版本。产品输出冻结后，才由评审人员与金标准逐条比对。本轮仅研究公开资料，未进行厂商产品扫描。
4. **逐文件留证**：要求导出原始机器可读结果，包括组件、版本、路径、识别/匹配方法、精确或范围匹配状态、置信/拒判状态、证据位置、SBOM 元素与扫描覆盖统计。无法导出证据链的结论标为“仅 UI 声称”，不与可回溯结果混为一类。

### 必报指标

| 指标 | 计算/报告方式 | 解释 |
|---|---|---|
| 身份识别精确率/召回率 | 组件家族身份按文件/嵌入组件逐项比较，分别报 precision、recall 和 F1；精确版本另算 | 不要把识别到库名算作版本正确。按组件家族和镜像分层，避免热门库掩盖长尾。 |
| 错误精确版本率（关键） | 厂商明确声称精确版本的真值错误数 ÷ 所有可核验的精确版本声明数；同时给分子/分母与置信区间 | 错报具体版本比拒判更可能污染漏洞/SBOM 结论。若抽样点很少，报告原始计数，不以百分比制造精度。 |
| 精确版本准确率与正确版本覆盖率 | 在可核验声明中计算正确精确版本数/已给精确版本数；另报正确版本覆盖率=正确精确版本数/真值可定版本数。给出版本但错误的项单列，不计入正确覆盖 | 准确率必须和覆盖率并列，否则总拒判产品也可能显得准确。 |
| 拒判/未知率 | 真值可定版本点中输出 `unknown`、范围版本或未给版本的比例，分类型报告 | 黑盒合理拒判可接受，但需要对照精确版本覆盖率与错误率评估。 |
| 未见版本行为 | 留出至少若干产品结果未知的版本构建/厂商分支（若现有两镜像包含），检查是否拒判、错误映射到邻近上游版，或仅报告组件身份 | 由于镜像数量和版本样本有限，对没有覆盖的版本只能报告个案行为；不能从两镜像推导普遍未见版本能力。 |
| 补丁状态准确性 | 单独使用有补丁源码/二进制差异证据的核验点，检查是否能区分“上游版本号相同但厂商已回补丁”等情况 | “漏洞数据库映射/版本推断”不等于验证补丁存在。补丁状态不得由 SPL 日期或上游版本直接替代。 |
| 覆盖与重复性 | 每镜像成功展开字节/文件数、遗漏/超限数、Android 分区/APK/APEX 等边界；固定条件重复扫描并比较结果 | 版本准确率只针对成功分析的范围，必须与解包覆盖同时报。 |
| SBOM 关联质量 | 组件/版本、文件路径、层级/宿主、依赖边、声明与观察冲突、CycloneDX/SPDX 导出逐项校验 | BOM 行数和非空版本字段不等于正确；确认一个文件中的多个组件不会被错误归到宿主。 |

### 建议通过门槛与决策

门槛应在看厂商结果之前确定。本项目可以先把**错误精确版本率为零（在已人工核验的关键版本集内）**作为安全门槛；正确精确版本覆盖率、未知率、展开覆盖和多版本归属则作为效用门槛单独协商。若样本量不足以支撑“零误报”统计结论，就报告观察到的 `0/N`，不宣称真实误报率为零。版本错报时查看是否保留证据/置信状态及能否抑制该版本进入 SBOM 漏洞结论。最终采购判断至少需重复扫描结果一致、人工可追溯、并在两镜像各自成立；不能用总组件数或厂商综合准确率作通过依据。

两份镜像适合做供应商筛选和缺陷发现，不足以测出跨产品、架构或版本的总体性能。若后续要评价泛化能力，应补独立厂商固件、不同编译器/优化配置、厂商分支和真正未见版本，并在评测前冻结真值与门槛。

## 对本项目的现实选择

截至本项目已有两镜像材料，版本覆盖仍很低。按统一修订标签的 32 个定向检查点，函数实验通过 31/32；其中 25 个已知版本点通过 24 个，7 个应保持未知的点全部通过。这个主动选择的诊断集不能外推成全量准确率，详见[实际实验记录](function-version-experiment-results-2026-11-18.md)。系统镜像还存在 APEX payload 未展开、超限 APK/内嵌库、复杂 ARM32/Thumb getter 和控制流等边界；原型已支持一部分简单 ARM/Thumb 形态。覆盖缺口需要容器支持和多版本代码参考库共同解决。

建议保留当前证据阶梯，并按投入顺序推进：

1. **先补覆盖记录和拒判质量**：对每个镜像记录已展开文件、超限/跳过区域、未识别格式和原因；未知必须能区分“组件未知”“组件已知、版本未知”“版本候选冲突”“没有可验证证据”。不要把未知静默填成 Android release、ABI 或 API 下界。
2. **建立小而可信的组件版本语料**：先针对 OpenSSL/BoringSSL、SQLite、zlib、curl、BusyBox 等高频家族收集有来源、版本标签、架构、编译器、优化配置和厂商改动状态的真实构建。完整文件哈希只证明与已知样本字节相同；代码/函数特征用于召回候选，不能单独证明上游版本。
3. **以函数级特征作候选检索，再做证据消歧**：对架构、编译器、优化与裁剪建立分层测试，保留候选相似度与支持/反证位置；对版本敏感 getter、明确 banner 和已定义符号等证据规定强弱等级。无足够证据时应输出候选或未知，不把最高分强制变成精确版本。
4. **版本与补丁分轨**：记录观测版本、厂商分支/构建标识、补丁证据、漏洞适用性为独立字段。对于厂商回补丁或 cherry-pick，基于具体代码/二进制补丁特征和产品证据核验，不从版本字符串或安全公告日期推断“已修/未修”。
5. **将商用工具用于候选和差异发现**：若 POC 通过上述盲测，可把工具结果作为额外证据/交叉检查或受控生产数据源；保留工具、版本、扫描时间、原始结果与证据位置。不要将供应商输出无条件写成真值，也不要把匹配方法未知的版本结果提升为本项目已确认结论。

产品验收应同时关注正确版本覆盖、错误版本和未分析范围。下一轮应以真实未知样本验证参考库与代码匹配的增益，商用工具可作对照；双方都使用独立真值，逐项记录补回了哪些版本、还有哪些遗漏。
