## 结论与本轮口径调整

**值得参考，优先采用版本估计、候选集合和源码差异检索。当前证据支持继续做这条路线，但不支持承诺两份固件达到 50% 或 70%。**

用户本轮明确接受相邻版本的误差，首要解决扫不到版本。因此，应当输出有依据的估计版本，并保留候选集合、依据和估计标记；无法精确区分相邻补丁版本，不应导致所有版本信息消失。此前把这类结果一律挡在精确版本门外，会低估它们对产品的用途。

后续同时报告：可用版本覆盖率（精确 + 估计）、精确版本覆盖率、候选集合宽度、同发布线相邻补丁命中、跨发布线错误、组件身份错误。候选集合包含相邻版本，与默认显示的单一估计版本命中相邻版本，是两个不同指标。参考库内版本不全时，保留未知/库外版本的可能性。

本次只评审、做只读固件清点和求解器实验；未把附件代码接入产品，未产生新的生产扫描覆盖率。

## 实际试验：接受相邻版本后，这个方向有价值

使用已校验来源的 5 个 Rust 家族、23 个源码发布版本和 46 个参考构建，检查附件 Rust 求解器的打分行为。参考索引采用这些构建中实际提取的源码位置，**没有实现附件提出的 tree-sitter 零编译 AST 索引**。这是一项评分规则试验，不能视作完整新算法的复现。

每次把真实源码版本的全部优化变体移出参考库，再查询该版本的已知构建：

| 结果 | 构建数 |
|---|---:|
| 输出单一其他版本，且该版本是同 major/minor 的相邻补丁版本 | 22 |
| 输出候选集合，其中包含同 major/minor 的相邻补丁版本 | 22 |
| 未输出版本 | 2 |

原代码把前 22 个结果写成 `exact`，这个标签需要改成估计；**按用户接受邻近版本的目标，这些输出仍然有用**。44/46 是这个有限、已知家族参考实验的结果，不能外推为固件准确率，也不等于 44 个单一估计值都已验证。

再把同一评分规则用于真实镜像中的 5 个目标文件，先过滤掉依赖 crate 的位置，只用目标 crate 和严格调用上下文：

| 目标 | 试验输出 | 解释 |
|---|---|---|
| aho-corasick | 估计 `0.7.20`，83/93 行位置匹配 | 可先给估计，尚无该目标的独立精确版本真值 |
| memchr | `2.7.3 / 2.7.4 / 2.7.5 / 2.7.6` | 保留候选，避免全留空；代表值需要额外排序依据 |
| regex-syntax | `0.6.27 / 0.6.28 / 0.6.29` | 同上 |
| ryu | `1.0.18 / 1.0.19 / 1.0.20` | 同上 |
| strsim | 37/61 行位置匹配，低于原阈值 | 继续测试行号偏移和源码改动容错，当前不称已解决 |

证据：`reports/version-corpus-20261118/guide-review/solver-counterexamples.json`、`target-estimate-pilot.json`。已有参考档案、源码与产物摘要保存在 `rust-sources/corpus.json` 和 `rust-reference-builds-*/builds*.json`。

## 直接影响当前项目的取舍

| 方案部分 | 评审结论 | 优先级与修改 |
|---|---|---|
| Rust 源码位置与行号差分 | 值得做；适合作为版本估计和候选检索 | 优先扩大到实际有位置证据的目标家族，先校验跨 crate 过滤、去重、宏和调用位置语义 |
| C/C++ Version-Delta | 值得做；可以减少逐版本全量构建成本 | 结合代码引用和目标组件归属，输出估计/候选；缺失特征不能单独确认更早版本 |
| 全文件/代码节哈希 + 公开二进制库 | 值得扩充，尤其有相同发行版产物的情况 | 根据实际未知文件选择来源；Android Bionic 产物与普通 Linux 发行版产物的哈希命中需要实测 |
| APK/JAR 全 DEX + 字节码参考库 | 当前确有输入缺口，值得优先补 | 需要接入 APK 主路径，不能只删除 framework JAR 中的一个 `break` |
| 显式版本等价集合 | 应采用 | 产品可展示估计值及候选，机器输出保留状态，精确统计单列 |
| 内容缓存 | 有用的性能优化 | 缓存不直接增加版本线索；先测耗时，保留每条文件路径与调用上下文 |
| 门控 BSim | 作为候选补充 | 实测相邻版本仍并列；先验证收益，再增加数据库服务 |
| unblob/LIEF 通用重构、RTOS/UEFI、License/关系图 | 对通用产品有价值 | 对这两份已能展开的 Android system 分区，不是当前版本输出的首要投入 |

## 输入缺口的只读实测

逐个读取两份 ext4 分区的 APK/JAR ZIP 目录，未解压或执行目标代码，未对 DEX 运行识别器。按路径统计，可能含相同内容的别名；不包含 APEX payload 内部文件。

| 镜像范围 | 含 DEX 的 APK 路径 | APK DEX 条目 | 其中次级 DEX | JAR 次级 DEX |
|---|---:|---:|---:|---:|
| Allwinner 提取出的 system 分区 | 89 | 90 | 1 | 0 |
| Android 16 system.img | 67 | 98 | 31 | 6 |

当前 `system_scanner.py::_analyze_apk_archive` 读取 manifest、Maven 元数据和 native 文件，**没有调用 DEX 分析**。附件所指的 `break` 实际在 `_scan_framework_jars` 内（当前第 924 行），只删除它不能覆盖上表中的 APK DEX。DEX 数量代表待分析输入，不能换算成将发现的库数量或版本收益。

检查附件列出的 dpkg/opkg/apk/rpm 四个数据库路径，在这两个分区均不存在。增加这些包数据库解析器对其他 Linux 固件有价值，但没有证据表明它能直接提升本次两镜像。

Android 16 的现有 2,134 次 ELF 分析中，有 1,785 个唯一文件哈希，349 次为重复内容（16.35%），重复字节约占 9.96%。没有逐文件耗时，不能从这个数据保证 365 秒降至 200 秒以内。`BinaryInventory.extract` 还使用 filename、component_type 和 location；缓存应分离内容证据与每次调用的身份/位置，不能复用同一个含旧路径的 Component 对象。

证据：`reports/version-corpus-20261118/guide-review/container-census.json`、现有 `scan/{allwinner,system}/file-observations.json`。

## 采用前需要改正的部分

1. **Rust 输入必须按目标 crate 过滤。** 附件第 481–484 行没有检查 `loc['crate']`。给它三条来自其他依赖、但同名 `src/lib.rs` 的位置，会输出目标 crate `1.0`，自称置信度 0.98。这属于组件归属错误，不是用户接受的相邻版本误差。
2. **标注估计，校准分数。** 第 516 行只要求行号匹配；三处列号全不符仍会输出 `exact`。单条位置也能通过 `min(3, len(obs))` 并得到 0.98。可保留为较弱估计线索，但不能把固定公式的数值当作已测准确率。重复位置需先去重。
3. **C/C++ 的缺失惩罚会制造唯一结果。** 第 336–347 行中，1.0 有两个原子，1.1 有相同两个及另三个原子；当 1.1 的另外三个原子被裁剪，求解器会返回 1.0。接受相邻误差后这个估计有用途，但候选应保留 1.1，不能称它已被证伪。跨组件复用字符串/常量还需要归属检查。
4. **332 个 NOTICE 候选不是 332 个第三方 C/C++ 发布版本。** 当前记录是 62 个 Rust 候选，加 270 个 `frameworks/*`、`system/*` 项目候选。项目目录关联也不等于二进制同源证明。分类有利于组织工作，但平台组件版本、内嵌第三方库版本必须分别描述。
5. **量化目标仍需批量实测。** 即便假设 332 个当前未知 native 行全部得到可用版本，固定 native 口径也只是 `(26+332)/774 = 46.3%`；固定全量口径为 `(154+332)/1129 = 43.0%`。Rust 62 个全部解决也只为全量口径增加约 5.5 个百分点。因此这是一条有价值的增量路径，尚不足以证明原口径 50%。
6. **getter 自报值与实现版本冲突要保留。** 附件第 531 行把 libevent getter 直接作为最终实现版本，过于绝对。已核对的同一源码 pin 中 configure 为 2.1.12，而 Bionic 头文件及目标 getter 为 2.1.8；可输出自报/估计版本并记录冲突，不能因来源是 getter 就认证所有实现代码属于该发布版。
7. **通用示例尚不是可直接合并的实现。** 熵检测 `read_bytes()[:4 MiB]` 仍先读取全镜像；LIEF 示例把所有动态符号当导出，未过滤未定义符号；没有 Mach-O 分支、PE 版本资源解析，也没有让 `.rodata` 的复制受预算约束。按节名哈希不能覆盖所有无节表/改节布局情况，更不能保证跨编译器命中。

上述反例只在内存 SQLite 中运行经检查的两个 Python 求解器；没有执行附件中的 shell、目标 ELF 或网络安装操作。

## 引用核查

Luna 完成了 7 项引用核查，主 agent 另行打开原始来源复核 PyXSieve、SBridge、Asteria-Pro 和 Ghidra #6098。

- [PyXSieve 原论文](https://arxiv.org/abs/2603.18693)支持历史发行版代码哈希及按库接口取版本的路线；不能直接认证附件的 Delta SQL 或固定打分公式。
- [SBridge 原论文](https://arxiv.org/abs/2606.28058)研究控制块级源码到二进制匹配，说明内联是问题；没有据此证明附件的 BSim 1-hop 加权和阈值。
- [Asteria-Pro 原论文](https://arxiv.org/abs/2301.00511)支持预过滤和重排动机；附件的 ResearchGate 链接题名与之不符。
- [Ghidra #6098](https://github.com/NationalSecurityAgency/ghidra/issues/6098)讨论 H2 规模与签名导出，不支持“必须 PostgreSQL 16”的结论。附件给出的 preScript 还需要实际脚本、版本和基准验证。
- [Rust 编译器调用位置说明](https://rustc-dev-guide.rust-lang.org/backend/implicit-caller-location.html)解释了宏、调用点与 track_caller 的语义；AST 节点坐标不天然等于二进制中记录的所有 panic 位置。零编译索引值得试，但需要独立验证。
- [cargo-auditable 的格式定义](https://github.com/rust-secure-code/cargo-auditable/blob/master/cargo-auditable.schema.json)不是完整 Cargo.lock JSON，部分格式还可能包括并未进入产物的依赖；不能笼统称为零误报真值。

完整侧任务记录：`reports/version-corpus-20261118/guide-reference-review.md`。

## 建议的近期执行顺序

1. 先接入估计版本与候选输出状态，让已有相邻版本结果成为用户可用的信息。用真实未知文件构建参考库，逐家族批量扩展，保留源码版本和构建先验各自的依据。
2. 扩展 Rust 源码位置索引；对同发布线的邻近候选允许估计，对跨 crate 或大范围跳版本作降级。先测 AST 索引的实际匹配率，再决定是否替代已编译参考位置。
3. 并行补齐 APK/JAR DEX 输入和实际出现的 Java SDK 参考资料；对 native 家族建设带归属的 C/C++ 差异索引。按新增可用版本数、邻近误差、跨家族错误和耗时排序后续投入。
4. 每轮重扫这两份原输入，保留原有全量口径，同时另列第三方视图。公开参考实验与目标固件的独立真值分开报告。50% 是尚待实扫验收的目标。
